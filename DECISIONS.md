# Decisions

Choices made where the BRD is silent or ambiguous.

1. **Repo root.** The BRD's outer `trustprobe/` folder is the working directory itself: `pyproject.toml` sits at the root next to the inner `trustprobe/` package.
2. **MCP SDK version.** Pinned to `mcp==1.30.0` (latest 1.x). PyPI's latest is 2.x, whose API differs from the one the BRD describes. All SDK calls live in `trustprobe/mcp_client.py` and the demo servers.
3. **Windows host.** The BRD targets Linux/macOS. The host code uses `pathlib` and passes mount paths to Docker Desktop as-is. Container paths are always Linux paths.
4. **Exit codes (10.6).** `Do not use` always exits 2. `Use with caution` exits 0 by default and 1 only with `--fail-on caution`, reading the BRD's "success unless --fail-on caution" as "CI passes unless asked to fail". Exit 3 is a scanner error, including Docker unreachable for a full scan.
5. **`validate` and Docker.** `validate` exits 3 when the Docker daemon is unreachable and the config asks for dynamic analysis. For static-only configs it only warns.
6. **`trustprobe/pipeline.py`.** Not in the BRD layout. It holds the scan orchestration (enumerate now; static and dynamic stages later) so `cli.py` stays thin.
7. **180 s limit.** The wall-clock timer starts when the container starts, not during the image build. A `threading.Timer` runs `docker kill tp-<nonce>`, which works regardless of what the asyncio loop is doing.
8. **strace filter and fallback.** `entrypoint.sh` tests each syscall name with strace and traces only those this strace/arch accepts (so `open` is skipped on arm64). That test also serves as the ptrace permission check. The scanner runs a short preflight container (`--check-strace`) first: without extra capabilities, then once with `--cap-add SYS_PTRACE`, then falls back to running untraced and records `monitor_note`.
9. **Build context.** The server directory is copied with symlinks preserved, not followed, and without `.git`, `__pycache__`, `.venv`, `node_modules`, so host files cannot be pulled into the image through a link. Package specs and requirements paths must match a conservative regex because they end up in an exec-form `RUN` line.
10. **Docker CLI environment.** The docker CLI process gets the MCP SDK's default safe environment plus `DOCKER_HOST`/`DOCKER_CONTEXT`/`DOCKER_CONFIG`/`DOCKER_TLS_VERIFY`/`DOCKER_CERT_PATH` if set. These configure the CLI only. Every `-e` passed to the container has an explicit value (tested).
11. **Audit log uses a named volume, not a bind mount (deviates from BRD 8.2).** The BRD mounts `<out_dir>/audit` into the container. On this Windows Docker Desktop (4.6.1) every new host folder triggers a file-sharing approval, and a declined approval made `docker run` fail ("user declined directory sharing"). The audit log now lives in a Docker-managed volume `tp-audit-<nonce>` mounted at `/audit` (the image pre-creates `/audit` owned by uid 10001, so the volume inherits that ownership). `Sandbox.read_trace()` copies the log to `out/audit/trace.log` before `cleanup()` removes the volume. This works the same on Linux and macOS.
12. **Docker-level failures are not "strace unavailable".** The strace preflight treats `docker run` exit code 125 as a sandbox error and raises it. Before this fix, the sharing error above silently produced `monitor: strace unavailable`, which would have weakened the verdict without saying why.
13. **`rugpull_math` swap rule.** The BRD says the description changes "from the 4th tools/list after the 3rd call". I implemented "once 3 `tools/call`s have happened, every later `tools/list` is poisoned" (the BRD's section 4.3 wording). Listings before any call, including the scanner's initial snapshot and enumeration, stay clean.
14. **`injectable_diag` stack-trace leak.** FastMCP wraps tool exceptions into `Error executing tool ...: <message>` with no traceback, so a raw `raise` would never produce the DY-010 finding the BRD expects. `read_note` therefore catches the error and raises `RuntimeError(traceback.format_exc())`, which puts the Python traceback in the error reply.
15. **`expected_findings.yaml` format.** Per server: `verdict`, optional `max_severity`, `static_only` (ids required in a static-only scan) and `full` (ids required in a full scan). They are "must include" lists, not exact sets, because heuristic low-severity rules (for example PM-002) may add extra findings.
16. **TP-001 and TP-005 cover tool fields only.** The BRD's sample YAML for TP-001 also lists prompt and resource fields, but section 7.2 says "tool, parameter, and schema fields", and PR-001/RS-001 exist to cover prompts and resources with the same patterns. Listing them in both would double-count one problem (and the penalty). TP-001 therefore looks at `tool.description` and `tool.param_descriptions`; TP-003 covers `tool.param_names` and `tool.schema_values`; PR-001 and RS-001 reuse the TP-001 and TP-005 patterns through `patterns_from`.
17. **Word boundary on TP-001's verb pattern.** The pattern `(read|open|cat|access|send|upload|post|include)[^.]{0,60}(...)` became `\b(read|...)\b[^.]{0,60}(...)`. Without it, "spread ... token" or "thread ... password" match. The intent is unchanged.
18. **SH-001 ignores names shorter than 5 characters.** Any 3 or 4 letter name is within 2 edits of something by chance. Equal names are never flagged either way.
19. **PM-002 severity.** A capability found in a tool but not in `declared_capabilities` is a low finding; one the operator declared is an info finding (so the report can still list it). With an empty `declared_capabilities` (all the demo configs) every inferred capability is therefore low (a 1-point penalty at heuristic confidence).
20. **PM-003.** Flags `additionalProperties: true`, or a schema with none of `properties`/`required`/`patternProperties`/`anyOf`/`oneOf`/`allOf`/`enum`. An explicit empty `properties: {}` is treated as a deliberate no-argument tool and is not flagged.
21. **PM-001.** `const` counts as a constraint along with `enum`, `pattern`, `maxLength` and `format`. The parameter name must equal one of the BRD's names (case-insensitive); it is checked at any nesting depth and through `anyOf`.
22. **Finding targets.** A resource's target is its `name` (falling back to its URI); a template's is its name or `uriTemplate`.
23. **Static-only verdict.** `scan --static-only` and `scan --surface` print a trust score and a verdict computed with `static_only=True`, so the best possible result is "Use with caution: dynamic analysis not run". The exit code follows the verdict.
24. **Rule fixtures.** `tests/fixtures/rules/<ID>.yaml` holds `cases` (name, expect match/no_match, optional severity, declared_capabilities, source, and a partial surface). A `{repeat: "x", times: N}` mapping expands to a long string. `tests/fixtures/surfaces/<server>.json` are saved surfaces of the four demo servers, so the demo-server static checks need no Docker.
25. **Clock between container and host.** The BRD says they share a kernel clock; with Docker Desktop the container runs in a VM. I measured the skew on this machine with repeated `docker exec date` samples against host time and it was within roughly 40 ms, well inside the attribution window (-0.05 s / +0.5 s). Instead of calibrating, `clock_is_plausible` checks every scan: if the trace lies more than 2 s outside the host's observation window, a note is added to the coverage and events are treated as unattributed (still detected, but reported on "server (idle)").
26. **At least 4 calls per tool.** The BRD relies on the default plan reaching 3 calls for the rug pull. A tool with one number-only schema would otherwise get fewer, so `plan_for_tool` adds numeric boundary calls (max, mid) and, if needed, repeats of the first benign call. Order: benign (required only), benign (all fields), hostile (one plain string parameter at a time, kinds in priority order across parameters), numeric boundaries, boolean and enum variants; trimmed to `max_calls_per_tool`. Enum-constrained strings are not attacked. `test_end_to_end.py` asserts `rugpull_math` gets at least 3 `add` calls.
27. **DY-006 and DY-007 merge per tool, not per call window.** When DY-006's shell proof exists for a tool, every DY-007 event for that tool is folded into the DY-006 finding as extra evidence (a benign call to a shell-using tool also spawns a shell, and reporting that separately would double-count the same flaw). Tools that spawn processes without a proven injection still get DY-007 (info if a shell was declared or inferred).
28. **DY-008.** Allowed write directories are the BRD's plus `/proc` (kernel interface, not storage). A relative path is resolved against `/app`, the server's working directory, and therefore counts as outside. Failed writes (read-only root filesystem) still count: the attempt is the finding.
29. **DY-003 evidence.** `matched` is the bare IP (`203.0.113.10`), because strace prints the address and port separately (`inet_addr("...")`, `htons(443)`) and a recorded proof string should appear in the evidence. The summary keeps `ip:port`. Idle-time connections are reported too (target "server (idle)").
30. **DY-001 / DY-002 across phases.** Prompts and resources are scanned for honeytokens like tool output. DY-002 also reports opens during startup and idle time, as the BRD allows.
31. **Snapshots.** Snapshot 1 ("initial") is the tool list from enumeration, taken before any call. The static rules re-run on `after_probes` and `after_delay` (tools only, no metadata rules); only findings whose id was not already reported are kept, and their evidence is prefixed with `[snapshot <label>]`.
32. **Coverage and verdict completeness.** Dynamic analysis counts as "not fully run" (so the verdict cannot be `no_issues_found`) when the session did not finish, a probe was skipped because strace was unavailable, a probe or static rule raised, or the time limit was hit. `coverage.dynamic` says which ("ran", "partial: ...", "skipped: static-only mode", "skipped: saved surface supplied ...").
33. **Observed capabilities** come from findings (DY-003 network, DY-007 or a DY-006 shell proof shell, DY-001 secrets, DY-002 secrets and filesystem, DY-008 filesystem); the report marks a capability "observed" over "inferred".
34. **Outputs and redaction.** `scan` always writes `results.json`, `report.html` and `surface.json` (also for `--static-only` and `--surface`), `audit/trace.log` and `logs/server_stderr.log` (sandbox runs). Everything written is passed through `Redactor`: host home, cwd, temp dir, config and output paths, the host username, and host environment values of 12+ characters. Paths are replaced before environment values, so a path under TEMP is never half-replaced. The stderr and trace logs are redacted after the run because Docker errors can quote host paths.
35. **`results.json` shape.** The `ScanResult` model plus extra keys: `meta.verdict_reason`, `meta.inventory`, `meta.server_name/version`, `meta.source` (as written in the config, relative), and `coverage.dynamic`, `static_rule_errors`, `dynamic_probe_errors`, `syscall_events`, `snapshots`, `capabilities_inferred/observed`, `notes`. The report is rendered only from this JSON, so `trustprobe report` needs no Docker.
36. **DY-009 and LR-001** (the optional LLM checks) are not part of M4/M5; they come with M6.
37. **`python -m trustprobe`** works as well as the `trustprobe` command; the end-to-end tests use it so they do not depend on the script location.
38. **Terminal steps 5 and 6** are printed after the analysis finishes, because the finding counts depend on the syscall log, which is only complete once the container has stopped. Steps 1 to 3 print live.
39. **LLM layer uses the official `anthropic` SDK, as an optional extra** (`pip install "trustprobe[llm]"`), imported only when `llm.enabled` and a key is present. The BRD does not name a provider; the key comes from the environment variable named by `llm.provider_env` (default `TRUSTPROBE_LLM_API_KEY`) and is passed to the SDK explicitly. Default model `claude-opus-5-5` (`llm.model` overrides it). Requests send `output_config={"effort": "low"}` only to models that accept it. No sampling parameters, prefill, forced tool choice or `thinking` are sent. I did **not** enable server-side refusal fallbacks (beta): a refusal simply means "no opinion", is counted in `coverage.llm.refusals`, and the deterministic result is unaffected. LLM code was tested only against a fake client; it has never called the real API in this repository.
40. **LR-001, DY-009 and explanations.** LR-001 lives in `trustprobe/llm.py`, not in the YAML rules, so the rule catalog stays the BRD's 19 deterministic rules. LR-001 severity maps low->low, medium->medium, high->medium (cap), and `hidden_intent: true` raises it to at least medium; DY-009 follows the same cap. Replies that do not parse as the expected JSON are discarded and counted. DY-009 is `requires_llm`: it is not run, and is not counted as a skipped probe, when the LLM is off or strace is unavailable, so it can never make a scan "incomplete". It only asks the model when the tool's calls produced notable syscalls (credential or non-runtime file reads, outside writes, non-loopback connects, spawned processes). Explanations cover the 10 most severe findings, are stored in `results.json` under `meta.explanations`, and are shown in the report marked as model-written.
41. **Privacy for LLM calls.** Only descriptions and short event summaries are sent, truncated to 6,000 characters, after replacing honeytoken markers with `<honeytoken>` and passing the text through the host redactor. Honeytoken files and tool outputs are never sent. Untrusted text is wrapped in tags and the system prompt says to treat it as data.
42. **`quick`.** It builds a config dict and calls `parse_config` directly, so no generated config file (which would hold a host path) is ever written. A directory is detected as Node when it has `package.json` (entry from `bin`, then `main`, then `index.js`/`server.js`/`main.js`), otherwise as Python (`server.py`, `main.py`, `app.py`, `__main__.py`; `requirements.txt` becomes the install step). `npm:` sources run `npx --no-install <package>` and `pypi:` sources run the console script named like the package; `--command` overrides either. PyPI specs must use `==` (a range would not be honoured); unpinned specs are allowed and flagged by MD-002. Output defaults to `out/quick-<name>/`.
43. **`node_echo` demo server.** The Node sandbox image had never been built or run, and I could not scan a third-party npm server (see item 44). `demo_servers/node_echo` is a dependency-free Node MCP server written for this: it exercised the Node image, strace under Node (no false positives), and the `quick` path for Node. It is a clean control, not part of `expected_findings.yaml`.
44. **Real public-server scan not done.** BRD 11.2 item 7 and the M6 acceptance check ask for a scan of a real public MCP server with each finding checked by hand. When I tried `trustprobe quick pypi:mcp-server-time==2026.10.28`, the environment's permission system declined running a third-party package's code, so I stopped instead of working around it. Nothing was recorded for it. To do it yourself: `trustprobe quick pypi:<package>==<version> --yes` (or `npm:<package>@<version>`), open the report, mark each finding true, false or unclear here, and tune the rule patterns and `tests/fixtures/rules/` from that.
45. **Demo rehearsal and backup recording** (M6) are not something I can do from here; the README has the three-minute script (BRD 12.3).
46. **Venv.** Development uses `.venv/` in the repo root (git-ignored).
